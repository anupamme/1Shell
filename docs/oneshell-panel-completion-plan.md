# 1Shell Panel 补全计划

> 状态:4.5 已完成 Panel 与配置的拆分,下一步进入"补能力"阶段。
> 制定日期:2026-06-23
> 目标:让 1Shell 从"多 VPS 连接 + AI/CLI 宿主"继续推进为"多 VPS 服务器面板中枢"。

---

## 0. 路线校准（2026-06-26）

本计划继续成立，但下一阶段不能把“补 Panel”理解成复制 1Panel / 宝塔的所有模块形态。1Shell 不是退回 2.0 的轻量 WebSSH，也不是每台 VPS 上常驻一套小面板；它应该是中心控制面，用本机/中心侧的能力替受控 VPS 节省内存和常驻负担。

证书管理是第一条需要校准的功能线：

- Panel 负责发现和展示：域名、证书路径、签发者、到期时间、站点绑定、ACME 日志入口、跨 VPS 过期预警。
- 任务模块负责重操作：签发、续期、DNS-01 / HTTP-01 策略选择、写入 Web Server 配置、reload、验证证书链和回滚建议。
- 1Shell AI 负责根据现场选择策略和编排步骤，但不能把证书能力做成一组固定表单来伪装智能。
- 受控 VPS 默认低驻留：能通过 SSH / 现有工具完成的，不新增常驻证书 daemon；确需定时续期时，优先生成最小 cron/systemd timer 或由中心任务巡检触发。
- 不做 1Panel 式“证书 CRUD 中心 + 应用商店式绑定流程”。那会让 1Shell 变成单机面板仿品，也会增加每台 VPS 的认知和运行负担。

一句话：**Panel 看得见，Task 做得成，AI 负责省内存和省心，不负责把 1Panel 重做一遍。**

## 1. 当前结论

4.5 做完的是"拆":

- 配置能力已经从 Panel 中拆出,成为独立"配置"板块。
- Panel 内部导航已经回到服务器面板主线:详情、主机、文件、探针、审计。
- 详情页从"运行情况"改为更接近服务器概览的入口。
- 文件浏览器完成了第一轮形态调整:VPS 选择放到顶部工具栏,文件区改为更适合浏览的表格布局。
- 文件浏览补上了远程目录缓存、顶部加载进度线、压缩和解压等基础体验。

下一步要做的是"补":

> 补全传统服务器面板里用户会期待、而 1Shell 目前还没有的确定性能力。

这个阶段不改变 1Shell 的核心定位:

- 1Panel 是单 VPS 面板。
- 1Shell 是多 VPS 管理中枢。
- 1Panel 可以作为单机能力参考,但不能照抄产品形态。

因此 1Shell 的 Panel 补全要同时满足两层:

| 层级 | 判断标准 |
|---|---|
| 基础模块 | 单台 VPS 上能发现、查看、操作、反馈、审计 |
| 中枢能力 | 能跨 VPS 汇总、筛选、对比、批量定位问题 |

只能服务单台 VPS 的功能是基础模块;能跨 VPS 汇总、筛选、对比、定位异常的功能,才是 1Shell 的 Panel 中枢能力。

## 2. 产品边界

### 2.1 Panel 做确定性能力

Panel 负责:

- 发现资源。
- 查看状态。
- 执行明确操作。
- 返回清晰反馈。
- 写入审计。
- 给出可复现的错误。

Panel 的按钮、状态、流程不能依赖 AI。用户点击"重启服务"、"查看日志"、"解压文件"、"发现 Docker 容器"时,后端必须有确定 API 和确定结果。

### 2.2 AI 只站在旁边

AI 可以做:

- 操作失败后解释原因。
- 根据当前页面上下文辅助理解。
- 帮用户把错误、日志、状态翻译成下一步建议。

AI 暂时不做:

- 不参与 Panel 主流程。
- 不把 Panel 操作包装成 AI 工作流。
- 不把工具流程做成复杂任务界面。
- 不替代确定性按钮、状态和错误返回。

### 2.3 不做的事

本阶段先不做:

- 复杂应用商店。
- 复杂自动化编排。
- 大而全的任务流编辑器。
- 把每个功能都做成 AI 工作流。
- 为了 AI 把面板流程复杂化。
- 把证书管理做成 1Panel 式常驻 CRUD 中心。

## 3. 补能力范围

优先补 1Shell 缺少、但服务器面板用户会天然期待的能力。

| 模块 | 先做只读发现 | 后做确定性操作 | 跨 VPS 中枢价值 |
|---|---|---|---|
| Docker / Compose | 容器、镜像、网络、卷、compose 项目发现 | start/stop/restart、查看日志、compose up/down/restart | 汇总异常容器、跨主机查看镜像版本、定位同名服务分布 |
| systemd 服务 | service 列表、状态、启动方式、失败原因 | start/stop/restart/reload/enable/disable | 跨 VPS 发现 failed 服务、对比关键服务状态 |
| 端口 / 进程 | 监听端口、进程、PID、用户、命令行 | 结束进程、跳转日志、关联服务 | 跨 VPS 找端口占用、暴露面、异常进程 |
| 日志 | journalctl、常见日志路径、按服务 tail | 下载、复制、按时间过滤、跟随日志 | 跨 VPS 汇总错误峰值、按服务聚合排查 |
| 证书状态 | 域名、证书路径、签发者、到期时间、站点绑定 | 续期任务入口、查看 ACME 日志、触发签发/续期任务 | 跨 VPS 找即将过期证书 |
| 站点 / 反代发现 | Nginx/Caddy/Apache 配置、server_name、proxy_pass | reload、测试配置、打开配置文件 | 跨 VPS 汇总站点、域名、反代目标 |
| 主机健康概览 | CPU、内存、磁盘、负载、网络、探针状态 | 跳转到文件/日志/进程定位 | 全局异常排序、筛选、对比 |

## 4. 实施顺序

### Phase 1:资源发现和只读状态

先把"看见"做好:

1. 定义每个模块的 discovery API。
2. 每个 API 返回结构化 JSON,不要只返回命令文本。
3. 每个结果带采集时间、目标主机、命令来源、错误详情。
4. UI 先做只读列表、详情抽屉、筛选、排序。
5. 全局页先汇总异常,单机页再下钻详情。

验收标准:

- 用户能在一个页面看到多台 VPS 的异常容器、失败服务、监听端口、证书到期和站点分布。
- 进入单台 VPS 后,能看到接近传统服务器面板的模块详情。
- 远程命令慢或失败时,界面显示加载、超时、stderr 和可理解的错误。

### Phase 2:低风险确定性操作

再补"能做":

1. systemd 服务 start/stop/restart/reload。
2. Docker 容器 start/stop/restart。
3. Compose 项目 restart / pull / up -d 的最小集合。
4. Nginx/Caddy 配置测试和 reload。
5. 日志下载、复制、tail。

验收标准:

- 每个操作必须有明确目标、命令预览、执行结果、错误返回和审计记录。
- 高风险操作进入确认或审批。
- 操作完成后自动刷新关联资源状态。
- 失败时能把 stderr、exit code、目标主机、工作目录返回给 UI。

### Phase 3:跨 VPS 中枢能力

最后补"为什么 1Shell 不是单机面板":

1. 全局异常视图:failed service、exited container、高负载、磁盘满、证书将过期。
2. 全局筛选:主机、标签、角色、地区、模块、异常类型。
3. 横向对比:同一服务在多台 VPS 的版本、状态、端口、日志。
4. 批量定位:一键筛出所有 `nginx failed`、所有 443 暴露、所有证书 14 天内到期。
5. 批量操作先只做安全动作,例如批量刷新、批量采集、批量打开详情;重启/停止类操作后置。

验收标准:

- 用户不是先选一台 VPS 再想问题,而是先从全局异常发现问题,再进入具体 VPS。
- 单机能力能自然复用为全局能力的数据来源。
- 跨 VPS 视图不是简单重复主机列表,而是能帮助对比和定位。

## 5. UI 形态原则

### 5.1 导航结构

Panel 继续保持左侧模块、右侧内容:

```text
Panel
├── 详情      全局健康概览 + 单机详情
├── 主机      主机仓库和连接状态
├── 文件      文件浏览、压缩、解压、上传、下载
├── 服务      systemd / Docker / Compose
├── 端口      监听端口与进程
├── 日志      日志检索与 tail
├── 站点      站点与反代发现
├── 证书      证书状态
├── 探针      探针、流量、采样
└── 审计      操作记录与失败原因
```

新增模块不必一次全铺进左侧。可以先在"详情"里放异常入口,成熟后再升为独立模块。

### 5.2 主机选择

不同模块可以有不同主机选择方式:

- 文件浏览器:顶部工具栏选择 VPS,保证文件区空间。
- 详情页:全局概览优先,单机详情作为下钻。
- 服务/端口/日志/站点/证书:默认全局汇总,筛选到单机后进入详情。

原则:

- 不在每个页面重复一个很重的左侧 VPS 列表。
- 全局问题先全局看,单机操作再选主机。
- 本机永远优先出现,但不特殊化成唯一入口。

### 5.3 加载体验

远程 VPS 可能很慢,UI 必须把"正在远程采集"说清楚:

- 顶部细进度线表示当前模块正在刷新。
- 旧数据可保留展示,标记为正在刷新。
- 返回上级目录或重复访问已缓存路径时先显示缓存,后台刷新。
- 单个主机慢不能拖死全局列表,全局聚合应允许部分失败。

## 6. 后端与审计原则

### 6.1 API 形态

每个模块至少有三类 API:

```text
GET  /api/panel/<module>/summary      跨 VPS 汇总
GET  /api/panel/hosts/:hostId/<module> 单机详情
POST /api/panel/hosts/:hostId/<module>/<action> 确定性操作
```

返回结构应统一包含:

- `hostId`
- `module`
- `collectedAt`
- `ok`
- `items`
- `warnings`
- `error`
- `rawCommand` 或 `commandRef`
- `durationMs`

### 6.2 错误返回

错误必须保留事实:

- 主机不可达。
- 命令不存在。
- 权限不足。
- systemd / docker / nginx 未安装。
- 命令超时。
- stderr 和 exit code。

不要只返回"操作失败"。

### 6.3 审计

读操作可以轻量审计,写操作必须完整审计:

- 谁发起。
- 对哪台主机。
- 哪个模块。
- 哪个动作。
- 操作参数。
- 执行结果。
- 错误详情。
- 是否经过确认或审批。

审计仍然不能记录密钥明文、token、私钥、密码或 `.env` 明文值。

## 7. 近期落地建议

建议下一轮不要同时补完所有模块,而是选一条最能体现"1Shell 是多 VPS 中枢"的路径:

### 推荐顺序

1. **systemd 服务只读发现**
   - 因为几乎所有 Linux VPS 都有 systemd。
   - 全局 failed services 很容易体现跨 VPS 价值。

2. **端口 / 进程只读发现**
   - 能和安全暴露面、站点、反代关联。
   - 适合做全局筛选和异常定位。

3. **Docker / Compose 只读发现**
   - 对开发者和小团队高频。
   - 后续操作价值大,但初期先看状态。

4. **日志基础查看**
   - 先支持 journalctl 和常见路径 tail。
   - 和 systemd / Docker 的详情页联动。

5. **证书与站点发现**
   - 从 Nginx/Caddy/Apache 配置和常见证书路径开始。
   - 先做状态和到期提醒,不急着做自动续期;签发/续期交给任务板块,不要在 Panel 里做一套完整证书 CRUD。

这样做的好处是:

- 每一步都能独立发布。
- 每一步都是确定性能力。
- 每一步都能先全局汇总,再单机下钻。
- 不需要先设计复杂应用商店或自动化编排。

## 8. 一句话方向

4.5 已经完成"拆":Panel 专心做服务器面板,配置回到配置。

下一步开始"补":先补资源发现和只读状态,再补可审计操作,最后补跨 VPS 汇总、筛选、对比和批量定位问题的中枢能力。
