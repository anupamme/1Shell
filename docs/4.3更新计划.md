# 1Shell 4.3 更新计划

> 状态说明：本文件记录 4.3 版本计划。4.2 已在当前工作树通过 git checkpoint 备份，4.3 从本计划开始重新定义主线。

## 版本定位

4.3 不再沿用原先“继续补默认 AI 工作流程序 / Agent 生态接入增强”的小补强路线。

4.2 已经完成登录 2FA、文件管理器写操作、Docker 容器视角写入提示、设置页独立化、默认浅色模式、Claude Code / Codex / OpenCode 接入向导、MCP standard profile 收敛等内容，已经足够承担一个小版本。

4.3 的新定位是：

```text
1Shell AI 智能体与自动化任务底座起步版本。
```

它要解决的问题不是“多做几个 AI 工作流程序”，而是先回答：

```text
1Shell AI 如何从多个分散的 AI 功能入口，补全为一个真正受控、可执行、可观测、可验证的智能体？
```

4.3 的目标不是一次性完成 Claude Code 级别的完整智能体，而是建立未来可承载它的最小 Agent Runtime Kernel，并优先让 1Shell AI 以通用 AgentRun 形式真实解决低风险运维任务。用户侧主词逐步从“AI 工作流程序”升级为“自动化任务”；Program 不再被视为创建阶段凭目标猜出来的起点，而应被视为成功 AgentRun 轨迹沉淀后的可复用封装。

## 核心判断

当前 1Shell AI 的问题不是“完全不能用”，而是：

- 主控界面、Program、Skill 创作、MCP `ask_1shell_ai` 等入口存在，但底层 Agent Runtime 不统一。
- AI 工作流 Program 能跑，但效果、效率、验证质量依赖模型自觉。
- LangChain / LangGraph / CLI 等能力迟早需要，但如果直接在某个局部强行接入，会造成未来架构割裂。
- Harness 已经是安全边界雏形，但工具、策略、事件、状态、预算、验证还没有形成统一智能体底座。

所以 4.3 的策略是：

```text
战略目标：补全 1Shell AI 为真正智能体。
当前战术：先做 1Shell Agent Runtime Kernel v0，让 1Shell AI 具备最小 observe / act / verify / trace 闭环，再从成功轨迹封装自动化任务 / Program draft。
技术原则：借鉴 LangChain / LangGraph，但不在 4.3 早期深度绑定第三方框架。
```

## 非目标

4.3 不做以下事情：

- 不全量迁移到 LangChain / LangGraph。
- 不把现有 Program Engine 直接替换成 LangGraph。
- 不先堆大量默认 AI 工作流程序。
- 不把“根据目标直接生成 Program”当作主要成功路径。
- 不把未验证的 Program 草案包装成可靠自动化。
- 不优先做完整 native CLI。
- 不把 Program 做成一套和主控台 AI、创作 AI 割裂的私有 Agent 内核。
- 不声称 1Shell AI 已经达到 Claude Code 完整能力。

## 4.3 版本主题

候选宣传主题：

```text
1Shell AI Agent Runtime 起步：让 AI 工作流从“能跑”走向“可控、可验证、可复用”。
```

或者更简洁：

```text
1Shell AI 智能体底座。
```

## P0：架构文档与边界确认

状态：计划中

目标：

在写大量代码前，先把 1Shell AI 的长期架构边界写清楚，避免 Program、主控台 AI、创作界面 AI、MCP Gateway、未来 CLI 各自长出一套不兼容的 Agent 运行时。

计划内容：

- 新增 `docs/1Shell AI智能体补全计划.md`。
- 明确 1Shell AI 的所有入口：
  - 主控界面 AI。
  - AI 工作流 Program。
  - Studio / Skill / Program 创作界面。
  - MCP `ask_1shell_ai`。
  - 未来 native CLI。
  - 外部 Claude Code / Codex / OpenCode 等 Agent 通过 MCP 接入。
- 明确 LangChain / LangGraph / MCP / Harness / CLI / MCP Server / Skill 的职责边界。
- 明确 4.3 先做 native Agent Runtime Kernel，不深绑定 LangGraph。
- 明确未来 LangChain / LangGraph 通过 adapter 接入，而不是成为 1Shell 架构的唯一内核。

验收标准：

- 文档能解释“为什么 4.3 不继续按旧计划堆默认 Program”。
- 文档能解释“为什么现在不全量引入 LangChain / LangGraph，但必须按未来可接入的方式设计”。
- 文档能成为后续编码任务的架构依据。

## P1：Agent Runtime Kernel v0

状态：计划中

目标：

抽出一个不绑定 Program、不绑定主控台、不绑定第三方框架的最小智能体运行时抽象。

核心对象：

```text
AgentRunSpec      一次智能体运行的目标、上下文、工具、策略和输出契约。
AgentState        一次运行的状态、阶段、工具调用、预算、结果和 artifact。
AgentEvent        可被 UI、日志、MCP、CLI 订阅的统一事件。
AgentToolCall     AI 产生的工具调用意图。
AgentToolResult   工具执行后的结构化结果。
AgentPolicy       权限、预算、风险、审批、工具白名单。
AgentArtifact     Program spec、报告、diff、部署计划、诊断结果等产物。
AgentCheckpoint   可恢复执行的状态快照。
AgentInterrupt    需要用户确认或补充输入的中断点。
```

第一阶段实现可以很薄，重点是先统一 envelope：

- source：`console` / `program` / `studio` / `mcp` / `cli` / `external-agent`。
- goal：用户或 Program 给出的目标。
- context：host、inputs、workspace、conversation、programId 等场景上下文。
- tools：本次运行可用工具列表。
- policy：预算、权限、风险、审批规则。
- outputContract：成功条件、结果结构、是否必须验证。

验收标准：

- Program Runtime 能被映射成 AgentRunSpec。
- 主控台 AI 和 Studio AI 未来能复用同一套 spec，不需要重写概念。
- 事件和状态命名不依赖 LangGraph，但能映射到 LangGraph 的 state/node/event/checkpoint 思想。

## P2：1Shell AI 最小 AgentRun 闭环

状态：计划中

目标：

优先证明 1Shell AI 不只是“能调用工具的 AI”，而是能以 AgentRun 为单位真实完成低风险运维任务，并留下可审计、可验证、可归纳的执行轨迹。

新的判断是：AI 工作流 Program 不应该主要从目标里猜出来。部署 GitHub 项目这类简单任务可以猜出 repo、host、port，但更复杂任务会涉及 Cloudflare token、DNS provider、第三方 API 权限、审批边界和验证条件，这些不能靠创建阶段的 AI 猜测。可靠的 Program 应来自：

```text
用户目标 -> 1Shell AI 真实执行 -> verifier/outcome 确认成功 -> Runtime trace -> 归纳并封装 Program
```

最小 AgentRun 需要具备：

- 多轮 observe / act / observe，而不是单轮工具调用。
- 结构化提问、请求 secret、请求 approval 的 interrupt 语义。
- 工具调用、命令结果、审批、secret 引用、artifact、verify、outcome 的 trace。
- 所有副作用工具仍经过 Harness / Policy / Audit。
- 成功由 verifier / outcome 判定，而不是 AI 自称完成。
- trace 能被后续 Program Creator 抽取 inputs / secrets / phases / budget / verify / policy。

首个验证任务建议仍然选择“VPS 基础健康巡检”，但先作为普通 1Shell AI AgentRun 执行，再从成功 trace 打包为 Program。

## P3：Trace-to-Program 与 Program Runtime v2

状态：计划中

目标：

在 1Shell AI 能真实完成任务并留下成功 trace 后，再优先解决现有 AI 工作流 Program “能跑但效果和效率不能保证”的问题。Program Runtime v2 的价值不是让 AI 在创建阶段猜更复杂的 YAML，而是让成功执行路径可以被可靠 replay。

核心升级：

### 1. Runner 状态与 Task 状态分离

当前容易把“AI step 执行完成”误认为“任务成功”。4.3 需要明确区分：

```text
runnerStatus：running / completed / failed / cancelled / waiting_approval / interrupted
taskStatus：unknown / success / failed / partial / blocked / unverified
```

示例：

```text
Runner completed，但 Task failed：部署命令执行完了，但公网访问 502。
Runner completed，但 Task unverified：AI 发布了结果，但 required verify 未通过。
```

### 2. Phase Contract

让 Program 可以声明阶段，而不是完全依赖 AI 自觉 `report_phase`：

```yaml
workflow:
  phases:
    - id: env_check
      label: 环境检查
      required: true
    - id: deploy
      label: 部署
      required: true
    - id: verify
      label: 验证
      required: true
    - id: result
      label: 结果
      required: true
```

Engine 需要记录每个 phase 的 started / done / failed / skipped / duration / evidence。

### 3. Budget Contract

给 AI step 增加硬预算：

```yaml
workflow:
  budget:
    max_tool_calls: 16
    max_commands: 8
    max_runtime_ms: 600000
    max_output_chars_per_command: 8000
```

目标：

- 防止重复探测。
- 防止命令过多。
- 防止上下文被长日志污染。
- 给 UI 展示“用了多少预算”。

### 4. Verify Contract

把成功验证从 prompt 规则下沉为 Engine 可执行契约。

最小版本先支持：

```yaml
verify:
  - type: http
    url: "{{ inputs.url }}"
    expect_status: [200, 301, 302]
  - type: tcp
    host: "{{ host.public_ip }}"
    port: "{{ inputs.port }}"
  - type: command
    run: "systemctl is-active nginx"
    expect_exit_code: 0
```

AI 可以执行和修复，但成功由 verifier 判定。

### 5. Success Guard

如果 required phase 未完成、verify 未通过、预算耗尽或出现待审批风险，AI 即使调用 `publish_result(status="success")`，Engine 也不能直接标记任务成功。

验收标准：

- 一个 AI Program 可以声明 phases、budget、verify。
- UI 能看到 runnerStatus 与 taskStatus 的区别。
- required verify 未通过时不能显示为任务成功。
- 超预算后任务进入 blocked / failed / partial，而不是继续无限循环。

## P4：统一工具调用 Envelope 与 Harness 对接

状态：计划中

目标：

让所有 AI 工具调用在进入 CLI / MCP Server / Skill / SSH / 文件系统之前，都先经过统一的 Tool Call Envelope 和 Harness / Policy 层。

计划内容：

- 定义统一工具调用记录：
  - source。
  - runId。
  - toolName。
  - args。
  - riskLevel。
  - capabilities。
  - host/path/workspace scope。
  - approvalRequired。
  - auditId。
- 现有 Program `execute_command` 先接入 envelope。
- 后续主控台 AI、Studio AI、MCP `ask_1shell_ai` 复用同一套 envelope。
- Harness 负责审核、阻断、注入安全参数、脱敏、审计。

验收标准：

- Program AI 命令执行记录可以用统一字段表达。
- 未来主控台 AI 不需要重新发明工具执行结构。
- 高风险工具能进入等待确认状态，而不是只靠提示词约束。

## P5：结构化命令结果与上下文控制

状态：计划中

目标：

减少 AI 工作流中长日志污染上下文，提高效率和结果质量。

计划内容：

- `execute_command` 返回结构化结果：

```json
{
  "exitCode": 1,
  "durationMs": 1234,
  "stdoutExcerpt": "...",
  "stderrExcerpt": "...",
  "evidence": ["nginx config test failed", "bind() to 0.0.0.0:80 failed"],
  "truncated": true
}
```

- 对 stdout/stderr 做最大长度限制。
- 对常见错误模式做证据抽取。
- AI 最终报告只引用关键证据，不直接拼接大段日志。

验收标准：

- 长命令输出不会把整个 tool loop 上下文拖爆。
- UI 仍能查看必要原始输出或摘要。
- AI 报告中包含证据而不是泛泛结论。

## P6：Program 黄金样例，而不是大量默认程序

状态：计划中

目标：

4.3 不追求一次内置很多 Program，而是先用真实 AgentRun 验证 1Shell AI 能做成事，再用少量从成功 trace 打包出来的黄金样例验证 Program replay。

候选样例：

1. VPS 基础巡检。
2. 服务日志诊断。
3. GitHub 项目部署。

每个样例必须包含：

- 输入字段。
- phase contract。
- budget。
- verify contract。
- 成功证据。
- 失败报告结构。
- 风险和审批策略。

验收标准：

- 黄金样例能覆盖读多写少、诊断报告、部署验证三类场景。
- 样例不是靠巨型 prompt 硬撑，而是依赖 Runtime 合同。
- 样例应尽量说明来源：目标草案、成功 trace，或 replay 成功后的 proven 状态。

## P7：主控台 AI 与 Studio AI 的接入预留

状态：后续规划 / 4.3 视进度

目标：

4.3 核心仍是 Runtime Kernel、最小通用 AgentRun 与 Trace-to-Program，但设计时必须为主控台 AI 和 Studio AI 保留入口。

其中“创造界面”后续不应继续按普通表单页扩展，而应逐步改造成 1Shell AI 的 IDE 界面：

```text
左侧：任务 / Program / Skill / 文件与资源导航。
中间：AI 会话、计划、diff、Program YAML、Skill 文档和 artifact 工作区。
右侧：AgentRun 状态、timeline、tool calls、checkpoint、interrupt、verify 结果。
底部：终端 / 日志 / CLI 预览。
```

这个 IDE 不是独立于 Runtime 的新系统，而是 Agent Runtime 的可视化控制台。后续 native CLI 也应复用同一套 AgentRun / checkpoint / interrupt / resume / cancel 语义，让 Web IDE 与 CLI 成为同一个智能体底座的两种入口。

后续接入方向：

- 主控台 AI：从普通问答升级为可以列主机、诊断、执行、验证、报告的运维 Agent。
- Studio AI：从 Skill/Program 创作辅助升级为可以生成方案、等待确认、写文件、检查 schema、修复错误的创作 Agent。
- MCP `ask_1shell_ai`：从简单委托升级为统一 AgentRun。
- 1Shell AI IDE：从“创建 Program 的页面”升级为面向运维、开发、Program 创作、Skill 创作和未来 CLI 的统一工作台。

验收标准：

- Runtime Kernel 的 source/context/policy 设计能表达这些场景。
- Program 私有字段不泄露到通用 Agent API。
- IDE 界面读取 AgentEvent / AgentArtifact / AgentInterrupt，而不是直接解析模型输出或 Program 私有状态。

## P8：LangChain / LangGraph 接入策略确认

状态：后续规划

目标：

不在 4.3 早期直接深度绑定 LangChain / LangGraph，但明确未来接入位置。

定位：

```text
LangChain：Model / Tool / Parser / Retriever / Memory adapter。
LangGraph：Graph Executor / Checkpoint / Interrupt / Resume adapter。
1Shell：定义运维语义、安全边界、工具权限、审计、验证闭环和 UI 事件。
```

验收标准：

- 4.3 文档与接口中不出现不可替换的第三方框架绑定。
- 后续可以新增 `LangChainModelAdapter` 或 `LangGraphExecutorAdapter`，而不是重写业务概念。

## 版本验收总标准

4.3 至少应完成：

- 1Shell AI 智能体补全计划文档。
- Agent Runtime Kernel v0 的最小接口或内部结构。
- 1Shell AI 最小 AgentRun 闭环：多轮 observe / act、Harness 工具调用、verifier / outcome、可审计 trace。
- Program Runtime v2 的第一批可靠性能力：phase / budget / taskStatus / verify / success guard 中至少完成核心闭环。
- 至少一次低风险真实 AgentRun 可以留下足以封装 Program 的成功轨迹；至少一个黄金 Program 从 trace 草案或 replay 流程中验证新合同。
- 所有真实工具调用仍经过 Harness / Audit / Secret Redaction。
- 不破坏现有 Program v1 基本运行能力。

如果 4.3 只完成文档和 Runtime Kernel 骨架，也可以接受；但不能再继续把“堆默认 Program”作为主线。

## 风险

- 过度工程化：Agent Runtime 设计过大，拖慢 4.3。
- 框架锁定：过早绑定 LangGraph，未来反而难维护。
- 场景割裂：只增强 Program，主控台 AI 和 Studio AI 继续停留在旧体系。
- 安全错位：MCP/Skill/CLI 工具绕过 Harness。
- UI 噪音：展示过多 Agent 内部状态，普通用户看不懂。

控制策略：

- 先定义最小通用对象，不急于实现完整图执行。
- 通用 AgentRun 作为最小验证对象，Program 作为 replay 和沉淀消费者；Runtime 命名和接口保持通用。
- 所有副作用工具先走 Harness。
- UI 默认展示摘要，高级信息折叠。

## 与 4.2 的关系

4.2 到此为止，作为“开箱体验与安全补强”小版本。

4.2 已完成内容为 4.3 提供基础：

- 登录安全：2FA。
- 文件与 Docker 写入提示：执行层反馈更可靠。
- Agent 接入向导：外部 Claude Code / Codex / OpenCode 可以更容易接入。
- MCP standard profile：外部工具面更收敛。
- Settings 独立页面：后续 AI Runtime 配置有落点。

4.3 在此基础上，开始补 1Shell AI 自身的智能体底座。
